# 决策：产品名「四野」的对外 ASCII 标识 —— 拼音 vs 英文意译

- 日期：2026-09-15
- 状态：**已全部实施**（含 GitHub 仓库改名 `KellenGO/MediaCrawler` → `KellenGO/SiYe`）
- 相关：`docs/features/tray-launcher.md`

## 背景

产品中文名是**四野**，但工程名一直是 fork 遗留的 `MediaCrawler`。两者并存造成了真实困惑：
`README.md` 首屏不得不专门澄清「本项目的产品主体是跨平台搜索，而不是通用爬虫控制台」——
**一个需要澄清的名字本身就是持续成本**。

同时名字在三个层次上不统一：

| 层 | 改名前的写法 | 例子 |
|---|---|---|
| 产品展示层 | 四野（中文） | UI 标题、落地页 `<title>` / `og:title`、release notes |
| 技术标识层 | siye（拼音小写） | `assets/siye-icon.png`、`SIYE_PORT`、`siye-landing-theme`、托盘 icon id |
| 工程遗留层 | MediaCrawler（英文） | 仓库名、Pages 路径、后端 EXE、zip 包名 |

问题：对外需要一个 ASCII 名时，是造一个英文意译名，还是直接用拼音？

## 关键事实（决定了选项空间）

- **意译没有好选项，且全部误导。** 四野 → FourWilds（像户外品牌）/ FourFields（像农业公司）/
  FourRealms（像游戏）。而且产品是搜小红书 / 抖音 / B站 / 知乎的，任何英文意译都解释不了它做什么。
- **拼音已经是既成事实。** 图标文件名、环境变量、localStorage 键、托盘图标 id，
  四个不同时期写下的标识全是 `siye`，没有一处是意译。
- **没有需要英文名的使用场景。** 本地运行、Windows 桌面端、只服务国内平台、落地页全中文。
  给中文用户看的产品配英文意译名，收益为零，代价是每次都要解释「为什么叫这个」。
- **仓库改名由 GitHub 兜底。** 改名后旧 URL（`github.com/KellenGO/MediaCrawler/*`、
  `kellengo.github.io/MediaCrawler/*`）会 301 到新地址，所以历史文档里的旧链接不会死。

## 选项

| | 做法 | 收益 | 代价 |
|---|---|---|---|
| A | ASCII 用拼音 `SiYe`，只摘产品语义，仓库名不动 | 消除对外误导；零外链风险 | 仓库名与产品名仍不一致 |
| **B** | 拼音 `SiYe` + 连仓库名一起改 | 彻底统一 | 已外发的 Pages / release 链接要重新攒收录 |
| C | 造一个英文意译名 | 理论上「更像产品名」 | 无好选项，且引入新的解释成本 |

## 决定

采用拼音，并最终执行了 **B**（当天先从 A 起步，随后决定一次做完）。

- **产品展示层**：继续用**四野**，不引入任何英文名。
- **技术标识层**：继续用 `siye`，不动。
- **工程层**：ASCII 标识统一为 **`SiYe`** —— 后端 EXE、仓库名、Pages 路径、zip 包名、`dist` 目录名。

**写法约定：写 `SiYe` 不写 `Siye`。** 连写会被英语读者读成 /saɪ/（像 sigh），
首字母大写拆成两个音节可读。中文场景一律「四野」，`SiYe` 只出现在需要 ASCII 的地方。

## 执行范围（2026-09-15 完成）

- GitHub 仓库改名 `KellenGO/SiYe`，本地 `origin` 同步更新；Pages 新地址 `kellengo.github.io/SiYe/`。
- 后端 EXE `MediaCrawler.exe` → `SiYe.exe`（`tray_main.py` 的 `MAIN_EXE_NAME`、
  `scripts/package_exe.py` 校验清单、`scripts/exe_clean_room_smoke.py`）。
- 打包产物：`MediaCrawler-Windows-x64.zip` → `SiYe-Windows-x64.zip`，
  `dist/MediaCrawler/` → `dist/SiYe/`，release workflow 的 artifact 名与 clean-room 路径同步。
- 外链：落地页 `canonical` / `og:url` / `og:image` / JSON-LD / 四处下载按钮 / 页脚，
  `site/guide.html`、`site/维护说明.md`、`docs/使用说明.md`、`docs/repository-map.md`、
  README、Issue 模板，以及 webui 三个组件里的当前项目链接。
- 面向用户的文案里的旧名（控制台提示、扩展弹窗标题、API 标题）改为「四野 / SiYe」。

## 刻意不动的四类

1. **源码文件头的 upstream 版权声明**（`# This file is part of MediaCrawler project.`）——
   `tools/file_header_manager.py:101` 会校验这个字样，改了会破坏文件头检查。
2. **localStorage 键** `mediacrawler_license_accepted` / `_theme` / `_language` ——
   改了用户要重新接受许可协议、丢掉主题和语言设置。
3. **上游与朋友仓库的链接** —— `NanmiCoder/MediaCrawler`（fork 来源）与
   `metaMMY07/MediaCrawler`（朋友的 Android 版）都保留原名。
4. **`MediaCrawler.spec` / `MediaCrawler.bat` 两个文件名** —— 改名会牵动
   `scripts/build_exe.ps1` 与 `docs/index.md` 的链接，收益低、易漏。

另外落地页 `keywords` 仍保留 `MediaCrawler`：那是搜索兜底词，不是产品身份。

## 后果 / 待办

- 落地页下载直链改成 `SiYe-Windows-x64.zip` 后，**在 v0.2.1 发布前会是 404**
  （v0.2 的 asset 仍叫旧名）。这个已有共识并接受：v0.2 原样不动，
  v0.2.1 重新打包后 asset 名自然对上，不需要为了让旧版可下载而保留旧名。
- 打包后需实机确认 PE subsystem 校验（`SiYe.exe=3` Console、`四野.exe=2` GUI）——
  文档已改，但还没在真实产物上验过。

## 被否掉 / 暂缓的方案及原因

- **英文意译名（C）**：无好选项，且会引入比 `MediaCrawler` 更难解释的新名字。
- **只摘产品语义、留着仓库名（A）**：当天先按 A 落地了一版，随后决定当天改完；
  A 的顾虑（v0.2 刚发、外链刚生效）由 GitHub 的 301 兜底，不值得再拖一个大版本。
