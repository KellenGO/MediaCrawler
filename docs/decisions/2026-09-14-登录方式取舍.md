# 决策：登录方式 —— 扫码 vs 浏览器扩展

- 日期：2026-09-14
- 状态：**倾向 A，待落地验证**（尚未实施）
- 相关：`docs/features/extension-login.md`

## 背景

扩展安装要开 `chrome://extensions` 开发者模式、再「加载已解压的扩展程序」，对普通用户是最大的劝退点。
目标是傻瓜式。问题是：能不能摆脱扩展？能不能把扩展功能内置进软件？

## 关键事实（决定了选项空间）

- **扫码不可能拿到浏览器那个会话 token。** 二维码是平台发给「发起请求的那个客户端」的一次性授权码，
  扫码确认后平台给**这个客户端签发一个新会话**；浏览器已有的 token 从不经过这条通道——
  否则二维码本身就成了会话窃取协议。
- 「使用浏览器那个 token」只有四条路：
  1. **扩展**（在浏览器进程内读）—— 现在这条路；
  2. **直接读 cookie 文件** —— 被 **App-Bound Encryption**（Chrome 127+）挡死，外部程序解不开；
  3. **CDP 连已打开的浏览器** —— 需要开启远程调试，Chrome 近版本对默认 profile 已不允许，且浏览器要常开；
  4. **复制 / 复用浏览器真实 profile 启动** —— 要用户关浏览器、体积上百 MB、文件被锁、跨版本脆弱。
- 因此**「把扩展功能内置进软件」没有干净实现**：扩展必须运行在「有登录态的那个浏览器」里，
  打包进 app 加载到自己的浏览器上也读不到东西。

## 选项

| | 做法 | 首次成本 | 后续维护 | 风险面 |
|---|---|---|---|---|
| **A** | 扫码为主，扩展降级为可选加速（**不删**） | 四平台各扫一次码 | 应用自己维护会话，月级偶发重扫 | 新设备登录，可控 |
| A' | 把扩展上架 Edge 加载项商店（一键安装） | 一次点击 | 跟随浏览器，零操心 | 同一 token 跨指纹复用（反盗号敏感）；审核不确定 |
| B | 彻底删扩展 | 四平台各扫一次码 | 同 A | 最干净 |
| — | 现状（开发者模式侧载扩展） | 劝退点 | 跟随浏览器 | 同 A' |

补充：扩展路的「设备账」更干净（平台只看到一个会话），但「行为账」更可疑
（**同一 token 从两个不同浏览器指纹使用**，正是反盗号系统重点盯的模式）；
扫码路恰好相反。两条路都有风险，不存在零风险选项。

## 决定

倾向 **A**：把**已经存在的**「内置扫码登录」从折叠备用提为主路径，扩展保留但不再出现在引导里。

理由：登录链路**已经写完**（`aggregate_search/worker.py` 的 `_run_login` + `/api/search/login`），
改动集中在前端优先级与文案，风险最低、可回退。

## 后果 / 待办

- 首次开箱要设计成**一次引导**：逐个平台「点击 → 扫码 → 自动验证打勾 → 下一个」，
  让用户感觉是一次设置，而不是配置四个平台。
- 接上登录失效提示（`webui/src/lib/accounts.ts` 已有 `connected → expired/login_required` 降级事件），
  让重扫变成一次点击。
- `site/guide.html` 的「先做两件事」可以砍成一件。
- 跑一两周真实使用，确认四平台扫码稳定后，再决定是否删扩展（B）。

## 被否掉 / 暂缓的方案及原因

- **内置扩展**：扩展拿不到登录态就没用（见上）。
- **直接读浏览器 cookie**：App-Bound Encryption 挡死。
- **上架商店（A'）**：不否决，与 A 并行评估；唯一障碍是审核不确定性。
